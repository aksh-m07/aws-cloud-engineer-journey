# Week 8: Infrastructure as Code with Terraform

This week I rebuilt the VPC from Week 5, but with Terraform instead of the console. The code is in `main.tf`. It uses the community `terraform-aws-modules/vpc/aws` module (version 5.8.1) to create a VPC called `training-vpc-tf` (10.1.0.0/16) in us-east-1, with two public and two private subnets across two availability zones and a NAT gateway.

About 15 lines of code turned into 19 resources in AWS. Only one of those is the VPC itself. The rest are the subnets, route tables, route table associations, an internet gateway, an Elastic IP, a NAT gateway, and the default security group, network ACL and route table that come with a VPC.

## The code

This is the whole `main.tf`:

```hcl
provider "aws" { region = "us-east-1" }

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.8.1"

  name = "training-vpc-tf"
  cidr = "10.1.0.0/16"

  azs             = ["us-east-1a", "us-east-1b"]
  public_subnets  = ["10.1.1.0/24", "10.1.2.0/24"]
  private_subnets = ["10.1.101.0/24", "10.1.102.0/24"]

  enable_nat_gateway = true
  single_nat_gateway = true
}
```

The `provider` block tells Terraform to use AWS in us-east-1, with the credentials from my AWS CLI setup. The `module` block is the VPC itself: its name, IP range, which subnets to create, and a single shared NAT gateway so the private subnets can reach the internet.

## The commands

**`terraform init`** sets up the folder. It downloaded the AWS provider and the VPC module into `.terraform/` and wrote a `.terraform.lock.hcl` file that pins the exact versions it picked. It doesn't touch AWS.

**`terraform plan`** is a preview. Terraform reads my code, reads the state file, checks what actually exists in AWS, and prints what it would change. My first plan said `19 to add, 0 to change, 0 to destroy`, and every resource had a `+` next to it because nothing existed yet. Plan never changes anything, so it's safe to run as often as I want. It's the step where I read every line before anything gets created.

**`terraform apply`** does the work. It shows the plan again, waits for me to type `yes`, then calls the AWS APIs and creates everything in the right order. The VPC went first, and the NAT gateway was the slow one at almost two minutes. It ended with `Apply complete! Resources: 19 added`, and I confirmed `training-vpc-tf` showed up in the VPC console with the same ID Terraform printed.

**`terraform destroy`** removes everything Terraform built, again after a `yes`. It uses the state file to know what to delete and handles the order itself, so the NAT gateway goes before the subnets it depends on. I ran it right after verifying the VPC, because a NAT gateway charges by the hour and isn't covered by the free tier.

## Why state matters

My `.tf` files only describe what I want. They don't say what already exists. Terraform keeps that record in `terraform.tfstate`, which maps each resource in my code to the real ID in AWS (for example, `module.vpc.aws_vpc.this[0]` maps to `vpc-045fae26e1485ef69`).

Everything Terraform does depends on it:

- **Plan and apply use it to decide what to change.** Terraform compares my code, the state, and AWS. Without the state it couldn't tell what it had already built, so it would try to create everything again.
- **Destroy only deletes what's in the state.** If I lost the state file, `terraform destroy` would think nothing exists and leave the NAT gateway running and billing me. That is why the state file matters as much as the code.
- **State can fall out of sync with AWS (drift).** If someone changes or deletes a Terraform-managed resource in the console, the state no longer matches reality and the next plan can behave strangely. Once Terraform manages a resource, every change to it should go through Terraform.
- **State can hold secrets in plain text.** I added `.terraform/`, `terraform.tfstate` and `terraform.tfstate.backup` to `.gitignore` before committing so they never reach GitHub. The lock file does get committed.
- **On a team, state shouldn't live on one laptop.** Teams usually keep it in a shared remote backend, like S3, so everyone works from the same record.
